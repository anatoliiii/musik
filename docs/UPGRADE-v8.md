# Обновление оригинального musik до схемы v8

Инструкция для владельца `torwin-job/musik` и существующих установок. Ветка для ревью: `anatoliiii/musik:pr/multiuser-postgres-mobile`. PR пока не создан. Ветка подготовлена поверх оригинального `main` на коммите `f8ede0e`; реализация мобильной совместимости и исправлений — `bb1d406`.

## Что входит в обновление

| Изменение | Последствия для установленного сервера |
| --- | --- |
| Общая схема v8, Alembic | До запуска нового player нужна миграция базы. Старый player после миграции использовать нельзя. |
| GORM в Go, SQLAlchemy в Python | Player и worker должны использовать одну и ту же базу и совместимые версии кода. |
| PostgreSQL 17 | Необязателен. Существующую установку можно оставить на SQLite. |
| Пользователи и музыкальные профили | Старые персональные данные закрепляются за одним владельцем установки и его основным профилем. Они не размножаются для новых пользователей. |
| OIDC, приглашения, локальные роли | Multi-user включается отдельно; браузерный вход требует OIDC и HTTPS. |
| Токены устройств | В multi-user заменяют общий API-токен. Секрет показывается один раз, хранится только хеш, срок действия — 180 дней. |
| Исправления ревью | Worker в multi-user, PostgreSQL-upsert статистики, конкурентное изменение администраторов и отзыв токенов при отключении пользователя. |

Single-user остаётся доступен: пароль браузера и общий `MUSIK_API_TOKEN` продолжают работать. Мобильное приложение обновлять не требуется. Стандартное оформление оригинала сохранено; личная тема из ветки `home` в эту ветку не включена.

## 1. Подготовка интеграции в оригинальный репозиторий

Проверить ветку можно до публикации PR. Следующие команды выполнять в чистом клоне оригинала или отдельном worktree, а не в каталоге работающего сервера:

```sh
git fetch origin main
git fetch https://github.com/anatoliiii/musik.git pr/multiuser-postgres-mobile
git switch -c review/multiuser-postgres-mobile FETCH_HEAD
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD
```

Если оригинальный `main` продвинулся, сначала интегрировать его изменения в review-ветку и повторить проверки. Перечень функциональности для ревью: переносимость БД → миграции и владение данными → OIDC и профили → мобильные токены → конкурентные операции. Проверять изменения оформления достаточно в стандартном интерфейсе оригинала.

После принятия изменений владелец оригинала объединяет ветку через свой обычный процесс и публикует согласованную пару player/worker. Для установки использовать один конкретный коммит или релиз обеих частей, а не независимо обновляемые `latest`.

До выпуска нужны проверки миграции копии реальной базы, API, интерфейса, мобильной сборки и восстановления бэкапа. Прохождение обычного `go test ./...` не означает, что каждый тест выполнился на PostgreSQL: многие fixtures остаются SQLite.

## 2. Выбор последовательности обновления

Рекомендуемый порядок:

1. Обновить код и SQLite до v8, сохранив single-user и существующие способы входа.
2. Проверить библиотеку, историю, избранное, миксы и мобильное воспроизведение.
3. При необходимости отдельно включить OIDC/multi-user и выдать персональные токены.
4. При необходимости отдельно перенести SQLite v8 в PostgreSQL.

Пересканирование музыки и повторный расчёт эмбеддингов для самой миграции не нужны. На каждом этапе должен оставаться бэкап предыдущего состояния.

## 3. Перед изменением базы

Зафиксировать текущий коммит/теги образов, Compose project name, используемые Compose-файлы, фактический том `/data` и путь SQLite. Сохранить `.env`, Compose overrides, настройки reverse proxy и OIDC. Секреты из `.env` не прикладывать к публичному PR.

Остановить все записи: player, worker, отдельные `musik watch`, задания cron/systemd и внешние команды, которые работают с этой базой. Убедиться, что длительные задания завершились или их прерывание приемлемо.

В существующем каталоге Compose, ещё до переключения на новый код:

```sh
docker compose stop player worker
```

Если установка использует готовые образы, во всех командах ниже применять `docker compose -f docker-compose.images.yml` и те же дополнительные `-f`/`-p`, что при прежнем запуске. Не менять project name: иначе Compose может создать другой пустой том. Не выполнять `down -v`.

### SQLite: согласованный бэкап

Следующий пример предполагает, что текущая база действительно лежит в `/data/db/musik.db`. Для нестандартной установки сначала заменить путь на проверенный. Команды создают backup в томе и копируют его на хост; рабочую базу не изменяют.

```sh
umask 077
mkdir -p backups/pre-v8
cp .env backups/pre-v8/env.saved
cp docker-compose.yml backups/pre-v8/compose.saved.yml
docker compose run --rm --no-deps -T --entrypoint python worker -c 'import sqlite3; from pathlib import Path; p=Path("/data/backups/pre-v8.sqlite"); p.parent.mkdir(parents=True, exist_ok=True); assert not p.exists(), "backup already exists: choose another name"; source=sqlite3.connect("file:/data/db/musik.db?mode=ro", uri=True); target=sqlite3.connect(p); source.backup(target); result=target.execute("PRAGMA integrity_check").fetchone()[0]; assert result == "ok", result; print("schema", target.execute("PRAGMA user_version").fetchone()[0]); target.close(); source.close()'
docker compose cp player:/data/backups/pre-v8.sqlite backups/pre-v8/musik.sqlite
```

Защитить каталог backup, поскольку база содержит личные данные и хеши действующих credentials. Отдельно сохранить пользовательские темы и файлы моделей из `/data`; музыку и внешние обложки учитывать в существующем плане резервного копирования. Бэкап только БД не заменяет бэкап внешних файлов.

Для установки без Docker остановить сервисы и сделать SQLite `.backup` в отдельный файл, затем проверить `PRAGMA integrity_check` и версию на копии. Не копировать один открытый `.db` без учёта WAL.

### PostgreSQL: если уже используется экспериментальная версия

С остановленными писателями сделать `pg_dump -Fc` конкретной базы, сохранить конфигурацию и проверить восстановление в отдельную базу. Данные доступа передавать через защищённую конфигурацию клиента. В бэкапе должна быть та же база, которую используют player и worker.

## 4. Обновление кода и конфигурации с сохранением single-user

В установке из исходников переключиться на принятый коммит оригинального репозитория. Если нужен предварительный запуск до merge, использовать подготовленную review-ветку из раздела 1 и явно считать это тестовым внедрением.

Не заменять существующую `.env` новым `.env.example`: перенести только нужные настройки.

Для стандартного Docker-тома:

```dotenv
MUSIK_DATABASE_URL=sqlite:////data/db/musik.db
MUSIK_MULTI_USER=0
# Существующие MUSIK_PASSWORD, MUSIK_API_TOKEN, MUSIK_SESSION_SECRET сохраняются.
```

Удалить активную настройку `MUSIK_DB_PATH`, если задан `MUSIK_DATABASE_URL`. Одновременное указание запрещено. В новом Compose URL базы по умолчанию задаётся самим файлом, поэтому прежний `MUSIK_DB_PATH` из `.env` тоже может вызвать конфликт.

URL SQLite относится к пути внутри контейнера. Для запуска без Docker задать абсолютный путь на хосте, например `sqlite:////srv/musik/data/db/musik.db`. Player и worker должны получать один backend и одну базу.

Для установки из исходников:

```sh
docker compose build player worker
docker compose run --rm --no-deps worker musik db migrate
docker compose up -d worker
docker compose up -d player
docker compose ps
docker compose logs --tail=100 worker player
```

Для готовых образов сначала закрепить опубликованный тег/коммит обоих образов через `MUSIK_IMAGE_TAG` и правильного владельца через `MUSIK_IMAGE_OWNER`, затем выполнить `pull`, отдельный `run ... musik db migrate` и `up` с файлом `docker-compose.images.yml`. Наличие ветки на GitHub само по себе не гарантирует публикацию образов этой ветки.

Штатный CMD образа worker также выполняет миграцию перед стартом; повторный запуск мигратора допустим. На время первой миграции все остальные писатели должны оставаться остановленными. Go player проверяет схему v8 и Alembic head `musik_8`, сам таблицы не мигрирует.

При запуске без Docker установить зависимости новой версии Python, собрать новый Go player, выполнить `musik db migrate` с окружением целевой базы, затем запускать worker и player. Не запускать старый бинарник поверх новой схемы.

## 5. Проверка после базового обновления

Проверить `GET /api/health`, журналы старта и реальное поведение:

- каталог и число треков соответствуют прежней установке;
- избранное, история, плейлисты и вкус прежнего владельца сохранились;
- радио и фиксированный плейлист воспроизводятся, события сохраняются;
- обложки и перемотка аудио работают;
- обновление миксов завершается и новые миксы видны клиенту;
- прежний пароль и общий токен работают в single-user;
- неизменённое мобильное приложение подключается, воспроизводит музыку и восстанавливается после перезапуска.

Для сверки числа строк и представительных данных использовать исходный backup и обновлённую базу. Успешный healthcheck не подтверждает сохранение всех персональных данных.

## 6. Отдельное включение multi-user

Подготовить OIDC-провайдера, доступный серверу по HTTPS, и зарегистрировать точный callback:

```text
https://music.example.com/api/auth/oidc/default/callback
```

Задать в `.env`:

```dotenv
MUSIK_MULTI_USER=1
MUSIK_PUBLIC_BASE_URL=https://music.example.com
MUSIK_OIDC_ISSUER=https://identity.example.com/realms/music
MUSIK_OIDC_CLIENT_ID=musik
MUSIK_OIDC_CLIENT_SECRET=<секрет клиента OIDC>
MUSIK_SECURE_COOKIE=1
```

Убрать `MUSIK_PASSWORD`, `MUSIK_API_TOKEN`, `MUSIK_AUTH_DISABLED`; CORS оставить same-origin. В multi-user общий пароль и общий API-токен запрещены, сервер с ними не запустится.

Остановить player/worker, убедиться в успешной миграции, затем создать приглашение первого администратора:

```sh
docker compose run --rm --no-deps player musik-player admin bootstrap --ttl 1h
```

Compose передаёт `MUSIK_OIDC_ISSUER` и URL базы из `.env`. Не добавлять `--db` при заданном `MUSIK_DATABASE_URL`, в том числе SQLite URL. Команда выводит секрет один раз; не публиковать его в логах или документации.

Запустить worker и player. Открыть в браузере:

```text
https://music.example.com/api/auth/oidc/default/start?invitation=<выданный секрет>
```

OIDC-вход активирует существующего владельца установки, сохраняет его прежний профиль и назначенные ему данные. Новые пользователи входят только по отдельным приглашениям и получают собственные профили. Bootstrap применяется для первого подключения владельца; повторный запуск после его активации не является способом восстановления произвольного аккаунта.

### Телефон без обновления приложения

Войти в веб через OIDC → «Профиль» → «Устройства и токены» → выбрать профиль и имя устройства → создать токен. Скопировать секрет сразу и вставить его в существующее поле API-токена приложения; адрес сервера — HTTPS URL. Поле пароля оставить пустым.

Каждый токен закреплён за одним профилем. Смена профиля в браузере не переключает телефон. Для другого профиля выдать другой токен. Токен можно отозвать или заменить; замена делает старый секрет недействительным. Отключение аккаунта отзывает все его токены, повторное включение их не восстанавливает. После удаления профиля связанные токены также отзываются.

Для обычного устройства доступны личные миксы, но недоступны управление аккаунтами, общей библиотекой и административные задания. По истечении 180 дней нужно заменить токен в существующих настройках телефона.

## 7. Необязательный перенос SQLite → PostgreSQL

Выполнять отдельно после принятого обновления до v8. PostgreSQL автоматически в Compose не добавлен: оператор предоставляет PostgreSQL 17 и сетевой доступ обоим сервисам.

1. Остановить всех писателей и сделать новый SQLite backup версии v8.
2. Подготовить отдельную пустую PostgreSQL-базу. Существующую рабочую базу не использовать как цель импорта.
3. Выполнить перенос из среды с новой версией `musik`, где доступны backup и целевая база:

```sh
musik db transfer --source /backup/musik-v8.sqlite \
  --destination "$MUSIK_TRANSFER_DATABASE_URL" \
  --report /backup/musik-transfer-report.json
```

Настройку `MUSIK_TRANSFER_DATABASE_URL` оператор задаёт только для назначения. Это отдельная переменная команды, не текущий URL приложения. В Docker backup нужно смонтировать в контейнер worker; пути в команде должны существовать внутри него.

4. Проверить успешное завершение, числа строк и контрольные суммы в отчёте. При ошибке не переключать сервисы на цель.
5. Задать одинаковый `MUSIK_DATABASE_URL=postgresql://...` для player/worker, удалить `MUSIK_DB_PATH`, сохранить необходимые пути `/data` и `/music`.
6. Запустить сервисы и повторить поведенческие проверки.

Команда переносит данные БД, включая владельцев, профили и хеши токенов, оставляя источник нетронутым. Музыку, внешние обложки и модели она не копирует. Если владелец уже активирован через OIDC, повторный bootstrap после переноса не нужен.

## 8. Откат

Миграции данных не поддерживают downgrade. Возврата старого кода недостаточно: старая версия требует базу из backup до обновления.

Остановить player, worker и внешних писателей. Сохранить неудачную обновлённую базу для диагностики. Восстановить прежние код/образы и конфигурацию, затем восстановить backup в проверенную целевую базу.

Для SQLite восстановление выполнять при остановленных сервисах. При замене файла учесть остаточные `-wal` и `-shm`: они не должны относиться к новой базе поверх восстановленного backup. Безопасный вариант — восстановить в отдельный каталог/том и явно направить оба старых сервиса туда. Не удалять прежний том до проверки восстановленной установки.

Для PostgreSQL восстановить dump в отдельную базу и переключить конфигурацию на неё. После отката повторить проверку каталога, персональных данных и воспроизведения. Записи, появившиеся после момента backup, при таком откате будут потеряны; длительность окна определить до обновления.

## 9. Известные границы проверки

На подготовленной ветке прошли Go-тесты, сборка и проверка синтаксиса JavaScript. В предыдущем ревью на отдельном PostgreSQL 17 проверялись миграция v8, DB/API-тесты и гонка создания/замены токена с отключением аккаунта. Это не подтверждает полную поведенческую паритетность всех путей PostgreSQL.

Выпущенная мобильная сборка на физическом устройстве/эмуляторе и отрисованный интерфейс ещё требуют проверки. Старый клиент не передаёт `event_id`/`impression_id`: неоднозначное сопоставление событий может вернуть 409, полная дедупликация его повторов не гарантирована.
