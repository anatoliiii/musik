# Обновление MUSIK до схемы v8

Инструкция для существующей установки SQLite/PostgreSQL и для подготовки
обновления оригинального репозитория. Переработана 2026-10-04 по результатам
реального переноса SQLite → PostgreSQL, включения OIDC и распределённых воркеров.

**Перед использованием нужен опубликованный комплект образов с исправлениями
из раздела «Готовность версии».** Коммит `8b82b06` содержит автоматику Compose,
но во время внедрения потребовались дополнительные исправления. Они находятся
в локальном рабочем дереве; наличие их в `home`, PR-ветке или GHCR нельзя считать
подтверждённым. Старый зелёный CI не подтверждает исправность этих новых путей.

Для конкретной установки на трёх серверах используйте
[отдельную инструкцию](THREE-HOST-OPERATIONS.md). Скрипты этой установки привязаны
к её путям и Compose overlays; повторять их на другом сервере не следует.

## 1. Что меняется

| Возможность | Условие |
| --- | --- |
| Схема v8, GORM/SQLAlchemy | Миграция до запуска нового player; совместимые player, worker и migrate |
| PostgreSQL в Compose | Необязательный профиль `postgres`, постоянный том, без публичного порта |
| Пользователи и профили | Включаются отдельно; старые данные остаются у прежнего владельца |
| Вход OIDC и приглашения | HTTPS, зарегистрированный callback, настройка reverse proxy |
| Токены устройств | Один профиль, 180 дней, секрет показывается один раз; клиент менять не требуется |
| Архивы и внешний GPU-воркер | Дополнительные исправления и настройка очереди; см. готовность ниже |

SQLite и single-user можно сохранить. Смена БД не требует повторного расчёта
эмбеддингов. Данные БД, аудиофайлы, кеши и пользовательские темы — разные части
установки: перенос БД не переносит остальные файлы.

Ветка `home` содержит пользовательскую тему. При подготовке изменений для
оригинала сохраняйте его оформление; не используйте `home` как замену review-ветке.
Точный коммит для ревью и выпуска нужно зафиксировать после включения исправлений.

## 2. Готовность версии

До публикации инструкции как готового автоматического обновления включить
исправления в согласованный комплект CI-образов и проверить следующие пути:

| Найденная проблема | Что должно входить в выпуск |
| --- | --- |
| Импорт самоссылок `tracks` нарушал FK | Перенос ссылок после вставки строк, в одной транзакции |
| Длинный fingerprint не помещался в PostgreSQL B-tree | Подходящий индекс и путь для уже созданной схемы v8; повторный migrate без новой миграции индекс не исправляет |
| Проверка `entity_vectors` давала ложное несовпадение | Каноническое сравнение строк независимо от сортировки SQLite/PostgreSQL, с сохранением повторов |
| Сохранение миксов вызывало SQLite `randomblob()` | Генерация идентификатора на стороне приложения |
| CPU worker забирал `full_rescan` без PyTorch | Разделение видов заданий между CPU и GPU |
| Player на физической реплике пытался писать | Обработка read-only БД, включая startup/reload и токены устройств |
| Первый Android Range получал несовместимый оригинал | Подготовка AAC/MP3 до первого ответа, стабильный Range |
| Android сообщал «нет доступных треков» после загрузки | Обновление индексов всех уже открытых профилей после завершения задания |

Факт успешного импорта конкретной базы не заменяет проверку миграции другой
установки. Релизный gate остаётся: конкурентные операции PostgreSQL, откаты
транзакций, поведение сервисов, восстановление backup и неизменённый Android-клиент.

Теги `branch-home` и `branch-main` изменяемые. Для воспроизводимого обновления
предпочтителен опубликованный `sha-…` или релизный тег. Все три образа приложения
должны иметь одинаковую OCI revision. Для локальной CPU-сборки нужна отдельная
проверка состава кода: общий тег сам по себе ничего не доказывает.

## 3. Подготовка существующей установки

Сначала записать:

- Compose project name и полный, упорядоченный список `-f` и `--env-file`;
- фактические bind mounts/тома БД, `/data`, `/music`, UID/GID доступа к файлам;
- текущий backend, схему, коммит, образы и локальные Dockerfile/overrides;
- все процессы записи: player, worker, GPU, lyrics, watch, cron/systemd;
- reverse proxy, OIDC callback, DNS и способ доставки музыки на standby.

Не заменять `.env` целиком примером. Сохранить конфигурацию, исходники локальных
патчей и прежние образы для отката. Если образ работающего контейнера удалён,
обычный `docker tag` по его ID не сработает: восстановление rollback-образа —
отдельный этап, до остановки контейнера. Не выполнять `down -v` и не менять
project name: это может создать пустые тома вместо существующей установки.

Проверить свободное место для backup, импорта, PostgreSQL, WAL и аудиокеша.
Сохранить состояния таймеров до их остановки. Дождаться завершения активных
заданий; не считать остановку таймера остановкой уже запущенного service.

### Резервная копия

Перед изменением backend/схемы остановить **всех** писателей и сохранить финальную
копию. Для SQLite использовать SQLite backup API или `.backup`; проверить на
копии `integrity_check`, `foreign_key_check`, версию и числа строк. Простая копия
открытого `.db` без WAL не является согласованным backup.

Для PostgreSQL сохранить `pg_dump -Fc` и восстановить его в отдельную базу.
`pg_restore --list` проверяет читаемость архива, но не доказывает возможность
полного восстановления. Сверить данные на восстановленной базе.

Зафиксировать количества как минимум `tracks`, `listening_history`, `favorites`,
`features`, `playlists`, `playlist_tracks`, а после включения multi-user —
владельцев, профили и права. Сохранять также отчёт переноса. Backup на том же
диске защищает от ошибки обновления; для потери диска нужна отдельная копия.
Не выводить `.env`, DSN и токены в общие логи.

## Автоматическое обновление через Compose (рекомендуется)

Этот путь подходит **стандартной установке с опубликованными CI-образами**.
После однократной настройки Compose, томов, HTTPS и авторизации обычное обновление
может сводиться к смене тега в `.env` и запуску скрипта. Внешние воркеры,
репликация и локальные сборки требуют дополнительных действий.

Нужны Bash и Docker Compose с поддержкой используемых файлов, `wait`, `up --wait`
и необязательных зависимостей. При наличии overlays с `!override`/`!reset` нужна
также их поддержка. Старый ориентир «Compose >= 2.20» недостаточен для всех
конфигураций. До остановки сервисов проверить разбор **полного** набора файлов
через `config --quiet` и наличие команд через `wait --help`, `up --help`.
Не использовать `run --pull`, если установленный Compose его не поддерживает;
загрузить образы отдельным `pull` до остановки приложения.

В `.env` выбрать владельца и опубликованный тег:

```dotenv
MUSIK_IMAGE_OWNER=anatoliiii
MUSIK_IMAGE_TAG=branch-home
```

Это пример адресации ветки, а не подтверждение готовности текущего образа.
CI также публикует `branch-<ветка>`, `sha-…` и релизные теги; PostgreSQL использует
собственный официальный тег. Указанный тег должен включать исправления раздела 2.

Для стандартной установки выполнить из каталога репозитория после подготовки
backup и остановки внешних писателей:

```bash
bash ./scripts/update-compose.sh -f docker-compose.images.yml
```

При нестандартных mounts передать прежний project name и **все** overlays в
исходном порядке. Не применять стандартную команду к распределённой установке
с локальным CPU-образом: проверка OCI revision может отклонить её конфигурацию.

Скрипт скачивает образы, проверяет общий OCI commit player/worker/migrate,
останавливает player/worker, запускает migrate, затем worker и player.
Он не останавливает внешние процессы, не обновляет reverse proxy/реплику и
не делает backup локальных Dockerfile/overrides. `depends_on` при обычном
`compose up` не обеспечивает остановку прежних писателей.

Migrate сохраняет backup при изменении существующей схемы; PostgreSQL-архив
проверяет через `pg_restore --list`. Полная проверка восстановления остаётся
отдельным этапом. При ошибке подготовки приложения остаются остановленными.
Повторять запуск следует после выяснения причины, сохраняя backup и отчёты.
Автоматического отката схемы нет.

## 5. SQLite v8 и перенос в PostgreSQL

Без смены backend сохраняйте прежнюю базу и том. URL SQLite относится к пути
внутри контейнера:

```dotenv
MUSIK_DATABASE_URL=sqlite:////data/db/musik.db
MUSIK_MULTI_USER=0
```

Не задавать одновременно `MUSIK_DB_PATH` и `MUSIK_DATABASE_URL`. Сохранить
существующие single-user credentials. Player проверяет схему v8/Alembic
`musik_8`; Go не выполняет миграции.

Перенос в PostgreSQL можно выполнить отдельным этапом после проверки SQLite v8.
Автоматический импорт также умеет мигрировать копию более старой SQLite;
первое обновление лучше разделить на этапы, чтобы локализовать ошибки.

Для встроенного PostgreSQL в `.env`:

```dotenv
COMPOSE_PROFILES=postgres
MUSIK_POSTGRES_USER=musik
MUSIK_POSTGRES_DB=musik
MUSIK_POSTGRES_PASSWORD=<случайный hex из openssl rand -hex 32>
MUSIK_DATABASE_URL=postgresql://musik:${MUSIK_POSTGRES_PASSWORD}@postgres:5432/musik?sslmode=disable
MUSIK_IMPORT_SQLITE=1
MUSIK_IMPORT_SQLITE_SOURCE=/data/db/musik.db
```

Пример требует замены пароля. `sslmode=disable` здесь относится к внутренней
сети Compose; для внешней БД настройте защищённое соединение. Встроенный сервис
не публикует порт на хост. POSTGRES-переменные инициализируют новый том:
изменение пароля в `.env` не меняет пароль уже существующей роли.

Сохранить прежний SQLite-том доступным для migrate. Цель импорта — отдельная
пустая БД, не рабочая заполненная PostgreSQL. Migrate сохраняет снимок SQLite,
обновляет схему копии, переносит данные и сверяет строки/хеши. Исходник остаётся
нетронутым; успешный маркер импорта записывается в транзакции с данными.
После успеха сохранить `/data/backups/*-transfer.json`, убрать флаг импорта и
повторить функциональные проверки. Если перенос завершился ошибкой, не очищать
цель вслепую и не запускать приложения поверх непроверенных данных.

## 6. Отдельное включение multi-user

После проверки БД подготовить OIDC-клиент и точный callback:

```text
https://music.example.com/api/auth/oidc/default/callback
```

В `.env`:

```dotenv
MUSIK_MULTI_USER=1
MUSIK_PUBLIC_BASE_URL=https://music.example.com
MUSIK_OIDC_ISSUER=https://identity.example.com/realms/music
MUSIK_OIDC_CLIENT_ID=musik
MUSIK_OIDC_CLIENT_SECRET=<секрет клиента>
MUSIK_SECURE_COOKIE=1
MUSIK_BOOTSTRAP_INVITE=<случайный секрет минимум 32 символа>
```

Удалить общие `MUSIK_PASSWORD`, `MUSIK_API_TOKEN`, `MUSIK_AUTH_DISABLED` из всех
активных env/overrides, а также подстановку общего Authorization и прежний внешний
OIDC forward-auth в маршруте MUSIK. Браузер входит через собственный OIDC MUSIK;
reverse proxy должен пропускать API, callback и Bearer устройства к приложению.
CORS оставить same-origin. Не менять настройки остальных сайтов proxy.

Migrate создаёт первое приглашение на 24 часа, без вывода секрета. Открыть:

```text
https://music.example.com/api/auth/oidc/default/start?invitation=<секрет>
```

Войти учётной записью прежнего владельца, проверить его данные и роль admin,
затем удалить bootstrap-секрет из `.env`. Не создавать bootstrap повторно после
активации владельца. Ручная команда `musik-player admin bootstrap --ttl 1h` —
альтернативный путь с отдельным TTL; её запускать с окружением выбранной БД,
без `--db` при заданном `MUSIK_DATABASE_URL`.

Телефон: «Профиль» → «Устройства и токены» → выбрать профиль → создать токен.
Секрет показывается один раз, хранится только хеш, срок — 180 дней. В неизменённом
мобильном приложении оставить HTTPS-адрес сервера, вставить персональный секрет
в поле API-токена. Токен не получает admin-права. Смена профиля в браузере не
переключает телефон; для другого профиля нужен другой токен. Ротация/отзыв
делают прежний секрет недействительным.

## 7. Внешний GPU, standby и локальный доступ

Эти компоненты не настраиваются одним изменением `.env` основного приложения.
Порядок и полный набор файлов вашей установки:
[THREE-HOST-OPERATIONS.md](THREE-HOST-OPERATIONS.md).

- CPU и GPU должны принимать непересекающиеся виды заданий; CPU без PyTorch
  не должен забирать `embed`/`full_rescan`.
- Реплицируется БД, но аудиофайлы и FUSE-кеш доставляются отдельно.
- Физическая реплика read-only. Здоровый player на ней не означает, что можно
  записывать историю, события, задания или управлять пользователями.
- После включения WAL-репликации отключить старые restore/snapshot-таймеры.
  Не восстанавливать dump в работающую физическую реплику.
- Split DNS вводить после проверки HTTPS на локальном адресе, сохраняя публичный
  hostname и OIDC callback. Не направлять DNS на HTTP-порт player.

## 8. Приёмка перед возвратом фоновых заданий

Healthcheck — первый шаг. Далее проверить:

1. Схему, отчёт переноса, данные прежнего владельца, историю, избранное и плейлисты.
2. OIDC-вход, приглашение обычного пользователя, изоляцию профилей и права.
3. Выпуск/ротацию токена устройства, старые треки и перемотку на телефоне.
4. **Новую загрузку при уже открытом профиле:** ZIP → завершённое GPU-задание →
   новый трек в браузере и Android без перезапуска player.
5. `POST /api/play` и затем аудио/Range. Ошибка «нет доступных треков» возникает
   до аудио, при отборе ID; успешный прямой GET stream её не исключает.
6. Для standby отдельно проверить WAL, наличие файла и proxy fallback на primary.
7. Для LAN — валидный HTTPS без `-k`, ответы обоих DNS, OIDC и загрузку через LAN.

Включать только нужные таймеры после приёмки соответствующего этапа. Не включать
устаревшие снимки и прежний GPU-расписатель поверх новой очереди автоматически.

## 9. Ошибки, с которыми столкнулись

| Симптом | Проверка и действие |
| --- | --- |
| pip долго ждёт `pypi.aya` | Проверить зеркало; для установки необходимых зависимостей использовать доступный источник. Сохранить версии PyTorch/NumPy, не обновлять весь ROCm venv |
| `unknown flag: --pull` | Проверить установленный Compose; использовать отдельный pull до остановки |
| `pipeline aborted` | Это может быть вторичным сообщением psycopg; получить исходный тип/причину ошибки без публикации DSN и персональных данных |
| `transfer verification failed ... entity_vectors` | Проверить исправление канонического сравнения; не отключать проверку переноса |
| `randomblob(integer) does not exist` | Исправить SQLite SQL в коде сохранения миксов; не создавать SQLite-функцию в PostgreSQL |
| `No module named torch` | Проверить, какой consumer забрал GPU-задание и его фильтр видов jobs |
| «нет доступных треков», browser играет | Проверить профиль, запрос `track_ids` и reload всех профилей после job; затем исследовать аудиопуть |
| VPS 404, primary 206 | БД и аудиофайлы обновляются независимо; проверить rclone и fallback. Не считать это доказательством ошибки Android |

При диагностике хранить подробности в root-only файлах. Не исправлять production
случайными SQL-патчами вместо воспроизводимой миграции/версии приложения.

## 10. Откат

Остановить всех писателей, сохранить неудачную БД/отчёты, восстановить прежние
образы и конфигурацию. Миграции не поддерживают downgrade: старому коду нужна
соответствующая копия БД. Восстанавливать в отдельный каталог/том/базу, затем
явно переключить сервисы. Для SQLite исключить использование чужого WAL/SHM.

Записи после момента backup при таком откате теряются. Не удалять исходные
каталоги и новый PostgreSQL до проверки восстановленной установки.

Физическую реплику нельзя сделать полноценным writable fallback одним запуском
player. При failover сначала исключить запись на прежнем primary, затем вручную
promote, проверить выход из recovery и перезапустить player. Возврат старого
primary требует отдельного восстановления репликации; автоматический failover
и `pg_rewind` в описанной трёхсерверной установке не настроены.

[архивы и LAN](UPLOADS-LAN-MOBILE.md),
[контракт БД](architecture/database-portability-contract.md).
