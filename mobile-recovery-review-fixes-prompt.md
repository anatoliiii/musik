## 1. Исправить подтверждённые проблемы

### A. Все worker-задания падают в multi-user режиме

src/musik/jobs/runner.py, _active_profiles(): функция перебирает conn.execute(...), но ORMConnection возвращает QueryResult без поддержки итерации.

Ошибка: `TypeError: 'QueryResult' object is not iterable`.

Исправь совместимость и проверь реальный путь process_job() при включённом multi-user, включая задания с явно выбранным профилем и без него.

### B. PostgreSQL отклоняет upsert статистики

В player/internal/db/history.go и других репозиториях встречаются:

```sql
plays=plays+1
shown=shown+excluded.shown
likes=likes+excluded.likes
```

В ON CONFLICT DO UPDATE текущие значения неоднозначны между целевой таблицей и excluded.

Проверь все такие запросы, включая BumpRecStats, BumpTransition, ApplyLifecycleEvent и RecordOutcomeTransition. Квалифицируй столбцы корректно.

Проверь вставку, повторное обновление, дедупликацию событий и сохранение истории на PostgreSQL и SQLite.

### C. Конкурентное изменение администраторов может оставить систему без администратора

player/internal/db/accounts.go, UpdateAccount(): проверка количества активных администраторов не сериализована.

Две транзакции могут одновременно снять роли двух разных администраторов, каждая увидит другого и успешно завершится.

Обеспечь инвариант «минимум один активный администратор» при конкурентном снятии роли и отключении аккаунта. Одной блокировки изменяемого пользователя недостаточно: операции над разными пользователями должны координироваться.

Проверь на независимых PostgreSQL-соединениях.

Сначала добавь воспроизводящие проверки, которые падают на текущем коде, затем исправления. Не ограничивайся тестами строк SQL.

## 2. Восстановить мобильную авторизацию

Сейчас MUSIK_API_TOKEN сохранён в single-user, но запрещён в multi-user; мобильной замены нет. Реализуй персональные непрозрачные Bearer-токены устройств.

### Модель

- Токен принадлежит User, а не музыкальному Profile.
- У пользователя может быть несколько независимых токенов: телефон, планшет и т. п.
- При создании токена в веб-интерфейсе выбирается профиль владельца; по умолчанию — его основной профиль. Сервер определяет профиль по токену, не требуя новых полей или запросов от мобильного клиента.
- Привязка профиля для выданного токена фиксирована: для другого профиля создаётся новый токен. Это предотвращает попадание отложенных событий старого клиента в другой профиль.
- Переключение профиля браузера не меняет профиль телефона.
- Владение выбранным профилем всегда проверяет сервер.
- При удалении выбранного профиля отзывай связанные токены. Не переназначай их автоматически другому профилю: старый клиент может продолжать отправлять события и использовать кеш предыдущего профиля.
- Используй криптографически случайный секрет с достаточной энтропией.
- В БД хранится только хеш секрета.
- Полный секрет возвращается только при создании и замене.
- Метаданные: id, имя устройства, владелец, активный профиль, дата создания, последнее использование, срок действия и дата отзыва.
- Выбери и документируй разумный срок действия.
- Отзыв блокирует последующие запросы этого устройства.
- Замена атомарно аннулирует старый секрет и выдаёт новый.
- Отключение аккаунта отзывает все его токены; последующее включение не оживляет отозванные токены.
- Секреты не попадают в URL, журналы и повторные ответы API.

### Права

- Мобильный токен позволяет пользоваться каталогом, воспроизведением и личными данными владельца.
- По умолчанию не даёт административных прав, даже если владелец — администратор.
- Не позволяет создавать/менять токены и управлять аккаунтами, приглашениями, общей библиотекой и административными заданиями.
- Управление токенами выполняется через авторизованную браузерную сессию с CSRF-защитой.
- Cookie-запросы сохраняют существующую CSRF-защиту. Bearer-аутентификация должна быть явно отделена от cookie-аутентификации; определи безопасное поведение при наличии обоих credentials.
- Общий MUSIK_API_TOKEN не возвращай в multi-user.
- Single-user авторизацию сохрани.

### API

- Спроектируй маршруты создания, списка, отзыва и замены токенов.
- Список никогда не возвращает секрет или его хеш.
- Bearer должен работать на обычных API, streaming, artwork и auth/me.
- Сохрани ожидаемый старым клиентом контракт auth/me, включая поля ok/auth_enabled, их типы и семантику. Новые поля допустимы лишь при подтверждённой совместимости парсера клиента. Не требуй от клиента понимания multi-user, OIDC или новых capabilities.
- Выбор профиля устройства выполняется при создании токена через веб. Новые мобильные экраны или вызовы API переключения профилей не требуются.
- Обеспечь изоляцию истории, избранного, вкуса, плейлистов и playback state.
- Проверь существующие session_id: при вводе токена другого профиля они не должны открывать или изменять состояние предыдущего профиля. Обработку устаревшей playback-сессии согласуй с существующим механизмом восстановления клиента.
- Для истёкшего, отозванного или неверного токена сохраняй ожидаемую клиентом обработку неавторизованного доступа. Для защищённых API используй 401; отдельно проверь старый контракт auth/me, если клиент ожидает там 200 с ok=false. Не возвращай мобильному API HTML-редиректы на OIDC.

### Веб-интерфейс

- Добавь раздел «Устройства и токены» в настройки аккаунта.
- Создание: имя устройства и профиль → однократный показ секрета с копированием в существующее поле токена мобильного приложения.
- Список: имя, привязанный профиль, создание, последнее использование, срок действия.
- Отзыв и замена отдельного токена.
- Впиши интерфейс в существующую тему home.

## 3. Обратная совместимость с неизменяемым мобильным клиентом

Сначала найди фактический исходный код мобильного приложения и проверь, что уже реализовано. docs/MOBILE.md содержит также план разработки — не принимай описанные там возможности за существующий код.

Если исходники клиента есть, изучай их только для восстановления контракта; не изменяй их, зависимости, настройки сборки или тесты клиента. Зафиксируй версию выпущенного клиента, с которой проверяется совместимость.

- Сохрани подключение по URL сервера + Bearer-токену через существующие настройки.
- Составь перечень реально используемых маршрутов, методов, заголовков, полей запросов/ответов, кодов ошибок и правил восстановления сессии.
- Проверь auth/me, playback events, session_id, streaming с Range, artwork, logout и восстановление после перезапуска.
- Реализуй серверную совместимость с существующими запросами; не требуй новых заголовков, profile_id, refresh-запросов, OIDC или обновления клиента.
- Проверь используемые клиентом операции с фоновыми заданиями. Если личные миксы раньше обновлялись через общий маршрут jobs, обеспечь ограниченную профилем совместимую операцию без выдачи прав на общую библиотеку и чужие задания. Не устраняй несовместимость раздачей административных прав.
- Для старых playback events сохрани допустимый формат и проверь серверную привязку к владельцу и профилю; новые обязательные поля не добавляй.
- Проверь поведение существующего logout и ошибок 401. Не требуй изменения клиентской логики.
- Не допускай записи отложенных событий предыдущего профиля в новый. Если старый протокол не позволяет надёжно различить такие события, явно опиши ограничение и безопасное поведение сервера, не заявляй неподтверждённую совместимость.
- Проверь аудио, обложки, фоновое воспроизведение и локальные кеши на неизменённой версии приложения. Серверная авторизация сама по себе не очищает клиентские кеши.

Если исходников клиента в доступном workspace нет:

- Не создавай новое приложение и не предлагай менять клиент.
- Используй доступную выпущенную сборку, записи запросов и существующие контрактные проверки. Документацию считай вспомогательным источником.
- Продолжай серверную работу, независимую от неизвестных деталей протокола. Отметь, какие детали требуют исходников, сборки или трассы запросов для подтверждения.
- Не объявляй совместимость с выпущенным клиентом подтверждённой только по серверным тестам.

Автоматический мобильный OIDC-вход через PKCE в эту задачу не входит.
